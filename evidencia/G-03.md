# G-03 · Alta de cliente y consulta por ID

**Fecha**: 2026-11-10
**Entorno**: frontend local con proxy a la API desplegada. Captura: `G-03-cliente-por-id.png`.

## Datos ficticios usados

| Campo | Valor |
|---|---|
| Nombre | Cliente Global Ficticio |
| Email | `cliente.global@ejemplo.com` |

## Pasos y resultado observado

| Paso | Acción | Resultado observado |
|---|---|---|
| 1 | Registrar el cliente | `POST /clientes/` responde **201**. Mensaje: `Cliente registrado con el identificador 3.` Aparece en la tabla de la sesión y en el selector de venta. |
| 2 | Recuperarlo por ID | `GET /clientes/3` devuelve `{"id": 3, "nombre": "Cliente Global Ficticio", "email": "cliente.global@ejemplo.com", "perfil": null}`. La vista Clientes lo muestra al buscar el identificador 3. |
| 3 | Repetir el email | `POST /clientes/` responde **409**. Mensaje del servidor: `Ya existe un cliente con ese email`. El formulario conserva el nombre ingresado y la tabla no suma filas. |
| 4 | Buscar un ID inexistente | `GET /clientes/999999` responde **404** y la interfaz muestra el mensaje de error de la búsqueda. |

## Decisión documentada

El backend de los capítulos 1 a 4 **no expone `GET /clientes/`** (sólo `POST /clientes/` y
`GET /clientes/{id}`). Por eso:

- La tabla «Clientes de esta sesión» muestra los clientes creados o consultados durante la sesión,
  en memoria. No se persiste en el navegador.
- La venta permite elegir entre esos clientes y exige verificar el identificador antes de usarlo.

Es la opción que la consigna contempla cuando el backend sólo ofrece la consulta individual.

## Evidencia

- `G-03-cliente-por-id.png`: cliente 3 consultado por ID y disponible para la venta.
