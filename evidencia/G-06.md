# G-06 · Rechazos

**Fecha**: 2026-11-10
**Entorno**: frontend local con proxy a la API desplegada.

## Casos ejercitados

| Caso | Petición | Respuesta observada |
|---|---|---|
| Cliente inexistente | `POST /ventas/` con `cliente_id: 999999` y un renglón válido | **409** `{"detail": "Cliente inexistente"}` |
| Libro repetido | `POST /ventas/` con `cliente_id: 1` y `[{libro_id: 1, cantidad: 1}, {libro_id: 1, cantidad: 2}]` | **422** `{"detail": "Libro repetido en la venta"}` |
| Historial después de los rechazos | `GET /ventas/?limit=100&offset=0` | 5 ventas; la última sigue siendo la 5. Ninguna operación rechazada quedó registrada. |

## Comportamiento de la interfaz

| Situación | Resultado observado |
|---|---|
| Libro repetido al agregar el renglón | Se rechaza antes de enviar: «Ese libro ya tiene un renglón en la venta; modificá su cantidad en la tabla.» |
| 409 del servidor al confirmar | Se muestra el mensaje del servidor (`Cliente inexistente`); el renglón, el cliente elegido y el total se conservan. |
| 422 del servidor al confirmar | Se muestra `Libro repetido en la venta`; el borrador se conserva. |
| Falla de conexión | Se muestra «No se pudo conectar con el servidor…»; el borrador se conserva y el historial no cambia. |
| Después de cualquier rechazo | El botón vuelve a «Confirmar venta» y queda habilitado: no se puede enviar dos veces. |

## Cómo se ejercitaron los rechazos del servidor desde la interfaz

La interfaz impide armar una venta con libros repetidos o con un cliente sin verificar, así que los
códigos 409 y 422 se obtuvieron llamando a la API con los cuerpos inválidos y, para el camino de la
interfaz, inyectando la respuesta de error en el cliente HTTP para comprobar que el borrador se
conserva y el mensaje se muestra. Las dos verificaciones están reflejadas en la tabla anterior.

## Conclusión

Ninguno de los rechazos modificó el historial y en todos los casos el usuario conserva lo que había
cargado.
